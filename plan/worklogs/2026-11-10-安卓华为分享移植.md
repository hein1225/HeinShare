## 2. 架构与关键决策

### 2.1 模块划分

- `core`（Android library）：协议与密码学，只用 `java.*` + kotlinx.coroutines，不碰界面，可在模块内直接跑 JUnit。
- `app`（application）：界面 + 系统集成（SAF、前台服务、通知、组播锁）。

### 2.2 平台适配点

| 平台约束 | 处理方式 |
|---|---|
| 组播包被系统丢弃 | 前台服务持 `WifiManager.MulticastLock`（`CHANGE_WIFI_MULTICAST_STATE`） |
| 后台被杀 | `foregroundServiceType="dataSync"` + `FOREGROUND_SERVICE_DATA_SYNC` |
| Android 13+ 通知 | `POST_NOTIFICATIONS` 运行时申请 |
| Scoped Storage | 发送侧走 SAF `ACTION_OPEN_DOCUMENT` / `ACTION_OPEN_DOCUMENT_TREE`，不申请存储权限 |
| 落盘 | 收到文件落在 `getExternalFilesDir(null)/HiShare`，重名自动加后缀 |

### 2.3 密码学实现全部**自带实现**，不依赖第三方库

AES-256-GCM / AES-128-GCM、ChaCha20-Poly1305、RSA-2048 OAEP、HMAC-SHA256、SHA-1/SHA-256 全部手写，
原因是 Rust 版用的就是这些，且 Android 侧需要与 Rust 端**逐字节一致**（尤其 OAEP 的 MGF1 用 SHA-1、
摘要用 SHA-256 这种非默认组合）。

### 2.4 密码套件协商不对称 → 「多套件依次尝试 + 明文兜底」

Rust 端发送方按**对端** settings 尾部 caps 选密码，接收方按**发送方** caps 判 Clear，两端规则不对称。
Kotlin 侧不猜：控制块与数据块都走 `openControlBlockAny` / `dfileParseChunkAny`，按 AES → ChaCha → 明文顺序尝试。

## 3. 本轮修掉的 4 个真实密码学 bug

这 4 个都是**单元测试暴露出来的**，此前 Rust 版一直没被向量验证过：

| # | 位置 | 症状 | 根因 | 修法 |
|---|---|---|---|---|
| 1 | `Crypto.kt` AES-GCM | GHASH 结果错误 | 规约常数符号写反 | 常数改为 `-0x1F00000000000000L`（= 0xE100000000000000） |
| 2 | `Crypto.kt` Poly1305 | tag 错误 | 末块 hibit 处理与 Rust 不一致 | 与 Rust 对齐：**每个块都带 2^128 位** |
| 3 | `Crypto.kt` Poly1305 | tag 错误 | 末 4 个字节的装配没有按 u32 截断 | 装配时 `and 0xFFFFFFFFL`（Rust 里是 u32 语义） |
| 4 | `Crypto.kt` RSA-OAEP | 解密返回 null | CRT 恢复公式写错 | `h = qInv·(m1−m2) mod p`，`m = m2 + h·q mod pq` |

另外把 Poly1305 的 MAC 数据长度字段从「比特数」改成**字节数的 64 位小端**（与 Rust `poly_input` 一致）。

> 教训：这 4 个 bug 全部是「看起来对、实际错」的类型，没有向量测试根本发现不了。
> 现在 `core` 模块里有 13 个用例，每次改动都跑。

## 4. 本轮还做的协议对齐（发现层）

对照 Rust `spawn_advertiser` 逐条核对后，改了三处：

1. **补上鸿蒙风格查询报文**（`advertisement_query_harmony` 对应实现 `Discovery.harmonyQuery`）：
   首字节 0x42 + 4 字节 token、mode=1、JSON 里带 `coapUri` 字段。
2. **补上「谁找到我我就单播应答谁」**：收到对端报文后，2 秒内向该对端单播一次
   `beacon(discovering=false)`（Rust 里就是这个逻辑，对端靠它确认「本机在线且可接收」）。
3. **广播节奏对齐**：beacon 每 900ms 广播+组播；harmony query 在没见到对端时每 1.5s 一次、见到后每 10s 一次。

同时把安卓端对外宣称的身份类型从 `14`（手机）改回 Rust 的 `12`（电脑）：
Rust 版以「电脑」身份广播是**真机验证过**能被华为端识别的路径，
宣称成手机反而可能被对端当成同类设备过滤掉。

### 8.2 「能被华为手机的华为分享扫描到」——逐条核对与补强

对照 Windows 版 Rust 源码逐条核验，安卓端发现层已具备该能力（A1–A9 全部满足），
要点与依据已写入 `port-spec/01-discovery.md` 第 11 章。

其中最关键的一条：**收到任何含 `device_discover` 标记的对端包就单播应答，不要求解析成功**
（Rust `app.rs:741` 的应答判断与解析块是分离的；安卓 `Discovery.kt:289` 与 `:291` 同样分离）。
华为端 query 变体解析失败时若不应答，对端超时后不再询问 → 设备直接消失。

**本轮补上的两个真实缺口**（都会直接导致「华为扫不到」）：

| 缺口 | 症状 | 处理 |
|---|---|---|
| B5 网络切换后不重建发现套接字 | 换 Wi-Fi / 断网重连后，手机再也扫不到本机 | `HiShareService.kt` 注册 `ConnectivityManager.NetworkCallback`（仅 Wi-Fi 传输），`onAvailable` 时重建发现套接字与 TCP 监听 |
| B6 `wlanIp` 可能取到 VPN / link-local 地址 | 对端按 wlanIp 回连失败，表现为「能扫到但传不过去」 | `Net.localIPv4()` 排除 `tun/tap/ppp/wg/docker/veth/vboxnet/virbr` 网卡与 `169.254.*` link-local |

另已在 `port-spec/01-discovery.md` 写明 B3（Wi-Fi 常连）、B4（同网段 /24）等安卓平台侧前提。

构建验证：`./gradlew :core:testDebugUnitTest :app:assembleDebug` 通过（13 个单元测试全绿）。
